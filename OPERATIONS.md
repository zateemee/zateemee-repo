# Zateemee operations and launch settings

New public flows: saved bridal showroom and shareable shortlist, account-backed saved gowns, compact quick view, dress search/filter/sort, responsive cover images, per-dress approved reviews, real contact submissions with reference numbers, appointment reservations for operator-published slots, and occasion cart size/quantity controls.
Private dashboard: /dashboard.html. Review/comment approval remains /moderation.html. Both require MODERATION_TOKEN when hosted. Local loopback development allows the owner to inspect the queue without a token. Use HTTPS, NODE_ENV=production and a strong random token stored only in server environment settings. The browser holds the entered token in memory. Do not put it in links or commit it.

## Email
RESEND_API_KEY, REVIEW_NOTIFY_EMAIL (atelier recipient), REVIEW_NOTIFY_FROM (verified sender) and PUBLIC_SITE_URL enable owner notifications. Reviews, enquiries and paid orders create persistent outbox rows; delivery retries every minute. Existing pending reviews remain in the moderation queue. Enquiries also queue customer receipts; reserved slots queue a reminder within 24 hours of the appointment while the Node server is running. Verified paid orders queue customer payment confirmations when Stripe supplies an email. All deliveries still require the configured provider. No email or SMS is sent without configuration. The dashboard can prepare a reply in the owner's email application.

## Appointments
Publish only confirmed future availability in the dashboard. Slots are stored in UTC and displayed in the visitor's local time zone. Reservation and enquiry creation are atomic so one slot cannot be reserved twice. Appointment receipt/reminder emails are queued, but calendar integration, cancellation/rescheduling and fees remain launch work. Do not promise delivery before email configuration. The preferred-date field remains a request if no published slot is selected.

## Payments
The payment adapter uses Stripe hosted Checkout. Activate only after confirming that the provided dollar prices are USD and the business can use Stripe. Set STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET, PUBLIC_SITE_URL (HTTPS), PAYMENT_CURRENCY=usd, STRIPE_SHIPPING_RATE (real configured rate), SHIPPING_COUNTRIES (comma-separated supported country codes) and PAYMENT_TAX_MODE=automatic. Configure Stripe Tax and product tax treatment to match the business. Publish real available sizes and availability for the two occasion dresses in the dashboard. No bridal product can be paid for through the adapter. Prices come from the server catalogue, never client input. Register /api/payments/webhook for checkout.session.completed and checkout.session.async_payment_succeeded. Payment is marked confirmed only after raw-body signature verification, matching session/currency/subtotal and a paid event; events are deduplicated. Test with Stripe sandbox before activating live keys. A mock provider test is not a real payment-provider test.

## Content and catalogue
The dashboard saves article drafts/published articles in atelier.sqlite; the journal API combines published entries with content/posts.json. Do not duplicate article identifiers across the two sources. Article text is plain text. The product dashboard updates sizing, production information and availability; supplied photos and descriptions remain in content/catalog.json. Accessory recommendations and editorial category photography await real accessory inventory/assets. Currency conversion and translated content are not activated: rate sources, base currency and translated copy need confirmation.

## Persistence and deployment
Run a Node server with native node:sqlite support and a persistent DATA_DIR volume. npm run build prepares dist; npm start serves the build with API handlers. A static host alone cannot run the database/payment/enquiry services. Keep the repository/scripts/content available to the Node process. Keep all secrets in hosting environment settings. Existing data files are ignored by Git and blocked by the static server.
Run node scripts/backup.mjs for consistent SQLite snapshots of reviews, accounts and atelier operations. Snapshots are under DATA_DIR/backups; copy them to secure off-server storage and define retention and restore checks before launch. Automatic backup scheduling, persistent hosting, mail/SMS credentials, customer receipts/reminders, account email verification/password recovery and strong admin authentication require infrastructure configuration before public launch.

## Verification
node scripts/integration-test.mjs exercises private admin access, contact persistence, outbox creation, appointment conflicts, journal publishing, occasion-only checkout, server prices, signed payment events and duplicate handling using an isolated database and mock payment provider. It never calls a live email/payment service. npm run build validates public artifact copying.

## Prepared deployment
Dockerfile and compose.yaml provide a Node 24 server, persistent named data volume and daily SQLite backup snapshots. Create a private .env file on the chosen host with the required settings, then build/start using Docker Compose. The web port binds only to host loopback until an HTTPS reverse proxy is configured. This configuration has not been deployed or built in Docker here. Snapshots share the volume and do not protect against disk/host loss: secure off-server copying, retention and restore testing are still required. No domain, cloud account or paid hosting was provisioned.
